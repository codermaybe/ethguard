# 多源不可信 RPC：方法语义与来源治理

状态：收敛后的讨论稿；不是新增实现规格或 ADR。

初始记录：2026-09-06。文档收敛：2026-09-07。评审补充：2026-09-07，见第 10 节。

本文维持多源均不预先可信的结构，明确不同方法应如何使用多源，以及来源筛选对这些保证的影响。此次仅调整文档，不修改代码；后续已接受的目标边界见第 8 节及决策记录，不代表运行时默认策略、成员资格或门槛已经改变。

## 1. 产品方向与讨论边界

EthGuard 的目标是在不预先信任某个 RPC 来源的前提下，提供符合方法语义、可解释的读取结果。`ethadapter` 保持 ethclient 风格的接口，参考建立、逐源校验和结果裁决主要由内部完成。

**按方法特点处理多源回答，是本项目的核心设计方向，也是相对于直接使用标准 RPC 客户端的重要价值。** 多源不是对所有调用做相同值投票：有些调用需要先固定共同参考，有些适合统计估计，有些只能描述节点本地状态，还有些应转发而不宣称一致性。

该方向已经部分实现。本轮应明确并补齐其契约，而不是从“所有调用统一 quorum”的错误前提出发重建架构。

以下边界继续成立：

- 不因商家名、公共列表收录、历史正常或响应较快而直接赋予数据权威。
- 不预先信任某个来源，不等于可以在任意恶意比例下保证数据正确。跨源一致只能在明确前提下佐证结果。
- URL 数量不等于独立控制者数量；本项目不能凭普通 JSON-RPC 证明来源独立性。
- 公共 RPC 不会配合运行客户端自定义的副本共识或响应签名协议。
- 保留健康筛选、冷却、恢复和新鲜度机制的可用性价值，同时评估它们如何改变本次参与集合。
- 不把读取裁决扩展为 Gas 优化、nonce 管理、签名、广播重试或交易生命周期管理。

## 2. 方法语义决定处理方式

分类单位是“方法＋参数／区块参考＋需要保证的结果语义”，不能仅按方法名或“可证明／不可证明”二分。以下区分现有行为与后续需要明确的边界；具体注册见 [client.go](../../client.go)，方法策略见 [rpc/methods](../../rpc/methods)。

| 方法类别 | 代表调用 | 当前处理 | 保证与待明确边界 |
| --- | --- | --- | --- |
| 确定性内容读取 | 区块、交易、receipt、chain ID、net_version | 逐方法归一化后 Strict；可显式启用 quorum | 同一对象、同一链参考下比较；存在性、未打包状态、重组及可选字段需按方法界定。多源一致不证明链身份或内容真实 |
| 依赖区块状态的读取 | balance、code、storage、transaction count、`eth_call` | 移动参考按策略锚定后比较；`eth_call` 对执行结果与 revert 分类 | 必须说明比较的是哪个区块、哪些执行参数；当前一致 revert 不代表错误文本或 revert 数据已验证；已接受的数据保护目标见方法契约第 0.5 节 |
| 范围／历史读取 | `eth_getLogs`、`eth_feeHistory` | 按策略固定移动高度／范围，归一化后 Strict | 高度固定不自动证明同一分叉；日志完整性、裁剪缺失、费用分位舍入需要分别处理 |
| 可变估计 | `eth_gasPrice`、`eth_maxPriorityFeePerGas`、`eth_estimateGas` | Median；estimateGas 还会锚定参考；结果为 Selected | 没有唯一正确建议值，不要求相同值 quorum；有效样本的组成仍会影响估计 |
| 节点本地观测 | peer count、syncing、listening | Local，从有效回答中按池顺序选择；结果为 Selected | 描述该来源的状态，不代表全网事实；健康不能证明本地报告真实 |
| 未注册／无专用策略的方法 | 默认配置下的扩展方法、`eth_sendRawTransaction` 等 | Forward，传输失败后顺序换源；结果为 Forwarded | 不宣称验证或共识，不等于多源广播或交易管理 |

`pending`、`latest`、`safe`、`finalized` 不能互换：移动标签如何改写、pending 是否拒绝或转发，必须由具体方法和调用入口定义，不在此统一改成旧的 finalized 数据。直接固定 hash、按高度固定范围与客户端声称 finalized，也具有不同证据强度。

2026-09-07 pending 方向已接受（0035）：逐方法支持，支持项以节点本地观测返回，永不 Corroborated；未支持项明确报错。路由由请求语义决定，不能由 quorum 失败触发。具体方法矩阵、来源选择及可见分类仍待列明。

2026-09-07 参考建立方向已接受（0036）：未投产阶段完整迁移旧自定义 resolver 扩展面，由库统一接收标签并验证共同参考，自定义能力在大部分任务完成后另议。项目特性是“保持标签语义的多源共同参考与调用内固定”；显式标签本身已有标准定义，不能宣传为 Ethereum 缺少标签支持。实现验收后在 README 展示实际用法及保证边界。

后续每个方法契约至少回答：

1. 回答是确定性事实、估计，还是来源本地视图？
2. 比较需要什么共同参考；是否会改写参数？
3. 哪些字段、空值和 JSON-RPC 错误可比较；归一化会忽略什么？
4. 什么条件返回 Corroborated、Selected、Forwarded 或错误？
5. 来源失联、异见、裁剪、重组会影响真实性、完整性、新鲜度还是可用性？
6. 额外请求、延迟与上游能力要求是什么？

当前 `Corroborated` 是方法策略要求得到满足的跨源佐证状态，**不是密码学证明或链上最终性证明**。根层 Call 可保留 Selected 供显式使用；ethadapter 的确定性读取不得以 Selected 静默替代所需佐证。保持调用签名不变，也必须说明参考变旧、冲突增多等行为成本。

| Chainlist | 内部解析工具供 soak 使用，不自动进入运行时投票池，不验证独立性 | [internal/chainlist/chainlist.go](../../internal/chainlist/chainlist.go) |

显式 quorum 的集合和门槛：

```text
N = 传给策略的本次观察集合大小
H = 配置硬下界
Q = max(H, floor(N / 2) + 1)
支持数 >= Q 才可能通过；还需满足回答有效性及状态分类规则
```

N 不是全部注册端点数，也不是成功回答数。[aggregator](../../aggregator/aggregator.go) 为每个 emission 建立 observation。`Attempted=false` 的成员不应因本地排队失败受到健康处罚，但仍保留在该次 quorum 分母中。“不计来源失败”与“不计多数分母”是不同规则。

时间边界同样重要：**请求前已过滤的来源不进入本次分母；入选后失败的来源保留在本次分母；下一请求重新筛选。** 这防止一次收集过程中门槛随失败降低，但没有固定跨请求的参与集合。

格式合法、及时返回的假数据在 pool 层仍可能记为成功。语义异见不自动触发冷却，冷却也不是识别撒谎的机制。

## 4. 多源不可信结构中的核心矛盾

按方法分流可以避免错误比较，但不能消除来源共同作恶、选择性失联和重复身份问题。对需要跨源佐证的确定性读取，必须区分以下前提：

- 诚实来源对同一参考和相同请求语义给出正确答案。
- 本次集合中恶意身份的数量有上界；多个 URL 可能由同一攻击者控制。
- 通过门槛足以排除仅由恶意来源构成的获胜簇。
- 足够多的诚实来源能够及时回答，才有成功的可用性条件。
- 分母不只随对抗行为与故障变化：负载与配额压力同样会把来源过滤出本次集合，且偏向方向与诚实性无关（历史观察见第 10 节，目标成员规则见0027）。

例如，若本次最多有 B 个恶意投票身份，要求获胜簇支持数大于 B，才能排除“获胜簇完全由恶意来源组成”；该推理还依赖共同参考、方法语义及校验正确。配置硬下界不会自行证明 B 的取值。

### 必须保留的反例

配置 5 源，3 个诚实源在请求前已进入冷却，剩余 2 个恶意源一致回答。若沿用当前 eligible 分母且 H=2：

```text
N = 2，Q = 2 → 两个通过语义校验的相同假答案可能获得 Corroborated
```

H>2 时该次请求拒绝；采用固定 5 源分母也会拒绝，但会付出不可用的成本。默认 Strict 同样不能阻止两个有效假答案一致通过。

这是安全假设可能随参与集合变化而失效的例子，不是“当前一定失败”，也不是取消健康筛选的充分理由。若诚实源是在 5 源入选后超时，显式 quorum 本次仍至少需要 3 票；下一请求的集合则可能改变。

### 仍需比较的成员方案

| 方案 | 价值 | 必须承担的问题 |
| --- | --- | --- |
| 当前 eligible 集合 | 自动绕过暂时不可用或过度落后的来源 | 需明确筛选后恶意预算与硬下界；不能沿用配置池的诚实比例假设 |
| 固定配置集合 | 多数基准稳定，容易解释 | 长期失效配置会阻塞；需要维护、退出与换源流程 |
| 有明确生命周期的投票集合 | 可将请求调度和投票成员变更分开 | 需要准入、退出、版本与切换规则，增加复杂度 |

上述为候选比较记录。现已按决策 0027 选择使用方显式管理投票成员：配置变化或运行时主动 add 等操作对后续调用生效，健康只影响调度、不自动缩小投票基准。默认已按决策 0028 选择固定多数方向，硬下界默认值仍待裁决；当前实现事实及反例保留用于迁移验证。

已接受的一次逻辑调用边界：调用开始时固定投票集合与门槛，贯穿参考建立、确认及业务读取，不因故障缩小分母。各阶段实际请求可为该集合的按需子集，但不得据此更换投票基准；参考与数据的支持证据分别记录。见决策 0025，跨调用成员变更已按决策 0027 交由使用方显式管理；缓存复用已按决策 0026 暂不纳入本轮目标。重试不能重复计票，也不能通过不断换源或降低候选高度“试到满意答案为止”。

健康与权重继续分开：低延迟和高成功率可以帮助调度，不证明回答真实。只查询最快的少数来源会改变本次样本；额外做一次全池审计不能为其他请求补足安全保证。不得仅因不赞同获胜答案就自动认定恶意。

身份与连接同样分开：IP、域名、证书、ASN、商家标签可辅助诊断相关性，不能证明控制者独立。重连、DNS/CDN 切换或服务端更换不能产生新票。端到端 TLS 转发与能解密重签的拦截代理不同，后者可能共同影响多家端点；新增传输策略应另行评审。

## 6. 评审场景与验收证据

下列是需要推演的场景，不是已经确认的漏洞清单。每个候选方案应给出返回状态、所依赖的前提及失败／恢复条件，不能只写“安全”或“失败”。

| 场景 | 必须回答 |
| --- | --- |
| 5 源中 3 诚实源请求前冷却；或入选后才超时 | 本次分母和门槛是什么；是否可能错误成功；下一请求如何变化 |
| 一个历史正常的源开始伪造合法回答 | 什么机制限制它的影响；不能假设健康冷却会识别伪造 |
| 攻击者持有多个 URL/IP；独立商家共享 CDN | 如何计算身份与恶意预算；是否重复计票或误合并 |
| 单源谎报极高／极低 tip 或 finalized | 在不同可用样本数下，是否能操纵过滤、候选高度或后续参与比例 |
| 诚实 finalized 为 84/100/100 | 给出 maxLag、模式和硬下界，再推导共同候选及确认结果，不能只说取多数 |
| 同高分叉；同源跨请求改变答案 | 区分参考变化、重组与同一确定性请求的矛盾；单次成功不自动给出跨请求一致性 |
| 日志漏项／空结果；历史数据裁剪 | 区分结果存在性、完整性和上游供数能力；说明异见或错误如何裁决 |
| Gas 估计差异；节点本地视图不同 | 是否属于自然差异，统计选择依据什么样本；不得误报事实共识 |
| 全网限流、网络分区及恢复 | 何时拒绝、何时恢复；是否隐含放松阈值或改变成员假设 |
| 重连、服务端替换、TLS 拦截 | 身份、票数、共享风险与已有证据如何处理 |
| 缓存期间成员／策略变化 | 命中结果基于什么参考和成员证据，何时重新建立 |
| 只查询最快少数源；本地并发槽不足 | 未选、未发出与失败的成员如何区别，哪些成员进入保证的前提 |

验证同时记录错误成功、错误拒绝、延迟、请求成本和恢复表现。随机掉线测试只能覆盖部分可用性，不能替代选择性阻断、假高度、重复身份、有效异见和成员变化的对抗测试。

## 7. 证明验证与外部方案的定位

### 7.1 证明验证是可选增强，不替代当前治理讨论

对能够取得可信根和充分证明的数据，密码学验证可以减少对执行 RPC 诚实比例的依赖。它值得独立评估，但不意味着必须先引入轻客户端，也不意味着未覆盖的方法都应做相同值投票。

可接受的保证应写为：在可信启动、正确的轻客户端／证明校验与所需新鲜度条件下，单个来源提供的有效证明可以验证特定数据相对于该根的正确性。恶意来源也可以提供真证明；所有来源拒绝供数时仍可能不可用。

候选评估必须区分：

- 可信 checkpoint、共识更新验证、execution root 的绑定与 RPC 数据证明，不能用同一个不可信 RPC 提供的根自证数据。
- optimistic、justified 与 finalized 的保证不同；有效旧证明不自动满足当前请求的新鲜度。
- 账户／存储证明、code hash 校验、交易／receipt 包含性和日志查询完整性不是同一种验证。逐条证明已返回日志存在，不足以证明没有遗漏；完整性需要覆盖查询范围的证据或经验证数据上的本地重建。
- 固定状态上的 `eth_call` 可评估经验证状态上的本地执行；`eth_feeHistory` 应分字段讨论；费用建议和 mempool 视图没有由简单证明给出的唯一正确值。
- 请求支持、成功返回、密码学验证、完整性和未验证转发必须分别列示。白名单不自动等于返回值携带验证状态，参数名称包含 optimistic 也不足以断言存在静默降级。
- 已有 Corroborated 表示跨源佐证；若增加证明验证，须单独设计如何区分证据强度，不复用同一名称模糊保证。

本轮不批准 proof 默认路由、验证 stub、sidecar 接入或新的对外状态。

### 7.2 外部实现只作为机制参考

| --- | --- | --- |
| eRPC | 回答分组、绝对一致阈值、错误类别、超时与争议行为 | 名为 consensus 不等于本项目的硬下界＋严格多数；处罚异见不自动适用于不可信多源 |

要求 provider 签署响应、公开欺诈证据或质押罚没，依赖上游配合与客观违规规则。签名首先证明谁作出了声明，不证明声明为真；变化的 latest 回答不自动构成欺诈。这些是额外协议方向，不进入当前普通 RPC 治理范围。

## 10. 历史评审补充的处理

早期评审曾提出限流不计连败、按诚实可用数设硬下界、优先 eligible 分母等选项。它们不是当前实施依据：成员由0027固定，门槛由0028–0029明确，调度由0031处理。尤其“按最坏诚实可用数确定安全硬下界”不能替代恶意预算约束。

保留的观察是负载／配额会影响来源可用性，以及方法契约应增量收敛。不得将历史“429即时返回所以不增加延迟”或“固定集合仅对网络有价值”作为已核验结论。
