# 项目路线图

更新：2026-11-17。阶段：主体框架已具备；本版完成现行文档系列整理与一致性检查，作为独立 Git 文档基线；代码问题与整体实现优化尚未开始。稳定发布仍待验收。

EthGuard 面向第三方 Ethereum execution RPC，提供保留方法语义的多源读取、明确的结果状态和可审阅的来源证据。后续目标是吸收现有框架与有效保证，减少重复维护的业务知识，逐模块简化实现，再以跨模块行为、兼容与成本证据验收。

## 1. 已完成基线与剩余缺口

| 方向 | 已具备 | 剩余工作 |
| --- | --- | --- |
| 方法面 | 固定 go-ethereum v1.17.10 的 47 项目标方法名称集合；27 个注册读 RPC，以及独立写入、订阅和派生能力 | 逐入口的参数、结果、错误和生命周期验收；方法数量不代表完整兼容 |
| 公开业务类型 | 目标方法及 root 扩展入口已迁至官方来源的 `ethapi` 生成模型；写入使用 `BinaryTransaction`；公开签名与调用方迁移已验收 | 审查内部对象路径仍维护的平行定义；后续类型修正沿统一来源审计与生成流程进入 |
| 规范来源 | 固定 execution-apis commit、独立原始向量、三项显式标准勘误和统一生成审计 | 按实际方法需要扩充覆盖，核对上游变化及勘误退出条件 |
| canonical 处理 | 两个独立交易查询与单收据 strict 路径已接入；单收据结果复用已完成 | 按方法证明共享对象准备的必要性与行为等价；接入数量不作为优化完成指标 |
| SimulateV1 | native root、EthClient view、Raw Call，以及生成请求／结果和 selector 模型 | 模拟块、内层结果、顶层错误及真实 provider 行为的逐项验收 |
| HTTP／WSS 与订阅 | 原生 HTTP、raw WSS、订阅及同源补取 | 相同输入的跨传输行为，乱序、背压、重连、取消和资源释放证据 |
| 结果与证据 | 业务结果、决策、附属材料及按调用预算保留的原始来源材料 | 字段完整性、错误 presence、历史分叉、真实 provider 观察及逐模块实现审查 |

公开业务类型迁移完成，不等于所有内部手写模型、校验或编码已消除。密码学与内容承诺仍需私有 geth 算法桥；公开签名与 `*ethclient.Client` 的 Go 类型身份不同，依赖 geth 接口的调用方需显式适配。

单收据验收基线为本地提交 `873c5b8`：`DecodeWithCanonical → PrepareTransaction → processReceipt` 复用已验证字节，保留 raw adapters、KeySource、准入顺序、请求绑定和私有 geth 检查。对象／方法回归、真实 Aggregator 对照、聚焦 race 与 vet 已通过。五次测量中微基准耗时约下降 44%，分配次数 931 → 479；三源 Aggregate 分配次数约 5386 → 4019，平均耗时约 3.641ms → 3.658ms，端到端耗时大致持平，不能据此宣称 CPU 使用量改善。证据来自本地脚本源与捕获 fixture，不扩张为真实 provider、其他方法或发布验收。

## 2. 当前执行顺序：先文档，后代码

已确定合同内的实现形状、重构、测试与成本验证交由 Flash 自主连续完成，不设等待主控响应的中间审计点。全部确定性任务结束后一次汇报，由主控整体审计。涉及产品保证、接受域或 F1／S1 未决政策时默认保留现行行为，记录差异并继续其他任务；不自行选边，也不以未获响应阻塞全程。

先阅读并重组全部现行设计／合同、公开与包说明，合并相互依赖或重复的文档，保留生成材料和历史证据身份。整份文档可以重写，旧文件在有效规则迁入并修复引用后删除，不保留空别名。执行顺序固定为：

1. 读取相关官方来源、现行合同、历史决策、实现与独立测试，明确业务目的、已有保证、实际差异和未决问题。
2. 写出一份内部一致的完整设计，交代职责、接口、状态、流程、错误、证据、生命周期、成本及未覆盖范围；分别标明现行事实、目标设计和待裁决内容。
3. 在新设计中明确采用哪些有效保证、取代哪些历史实现安排，以及必要的兼容影响。历史依据由 Git 和决策引用保留；明确列出已取代的结论，不让执行器拼接多代相互冲突的说明。
4. 完成全系列事实、引用、术语、生成索引及文档互锁核对，保存一个独立 Git 文档版本。本步骤之前不处理代码发现、不实施对象或模块优化。
5. 从已保存的文档基线制定明确代码任务，按行为切片实施并用独立预期、真实调用链和适当成本验收。文档完成、代码完成和整体验收分别记账。

完整重写文档不自动授权改变业务合同。历史实现方式可以重选；成员分母、裁定门槛、保证范围、请求绑定、错误归因、健康及证据保留等变化须明确说明和裁决。普通编译或测试失败在已授权范围内修复，不变成反复的阶段审批点。

长期有效的设计和实际状态维护在已有正式文档中；阶段性执行表、审计草稿和非关键总结仅存 docs/tmp/，统一忽略、不纳入 Git，不另设 docs/design/tmp。生成索引仍由工具维护，不能把新设计写入生成文件。此路线图记录进展与依赖，方法合同和模块设计拥有具体行为。

## 3. 消除手写平行业务定义

目标是同一业务事实只有一个权威定义。审查对象包括 DTO、字段表、required／nullable、标量格式、分支、规范编码和输出投影；按职责而非按文件或是否手写决定保留与删除。

| 知识 | 目标归属 |
| --- | --- |
| 官方字段、基础形态、标量约束和分支 | 官方原始来源 → 已审计的勘误／生成策略 → 统一生成模型 |
| 有样例支持的有限生态兼容 | 方法拥有的明确规则，先形成候选再执行适用检查 |
| 方法参数关系、响应范围和请求绑定 | 方法／对象模块，消费已验证表示 |
| 签名、hash、bloom 与内容承诺 | 私有算法实现，保留其独立保护职责 |
| 聚类、裁定、来源归因、健康和材料保留 | 执行模块，消费阶段结果，不复制 schema 知识 |
| 独立测试向量及预期 | 保持独立，避免与生产实现共享同一错误 |

首轮静态发现已移入 [方法合同的待处理事项](method-contracts.md#6-待裁决与待实现事项)，涉及 FeeHistory、AccessList、共享 Log 及其接受域。现阶段仅记录，不继续调查、改代码或并行展开优化。公开模型完成不免除内部审查，也不能据此重做已完成迁移。

### 逐模块优化重点

| 模块 | 审查与优化方向 |
| --- | --- |
| aggregator | invocation 状态与路线冻结；各阶段结果的统一消费；fault、health、证据的归属；成功、失败、取消和提前返回的清理责任 |
| rpc／resolver | 比较、裁定与提交的职责；共享内核与有意义的策略差异；错误分类及分母不变量 |
| methods／objects／codec | 生成合同与方法规则的分工；对象准备结果复用；投影、兼容和规范编码的重复 |
| pool／reference | 成员、候选资格、调度、freshness 与健康政策的归属，避免跨模块重复推断 |
| transport／subscription | 连接和订阅状态机、背压、重连、取消、预算及资源释放 |
| runtime／公开入口 | 唯一装配与 typed projection；转换适配、跨层知识及公开合同一致性 |

优化要减少当前实现需要同时理解的规则和修改位置，避免仅把复杂性转移给其他模块。每个模块交付须说明有效合同、目标与实际差距、被删除的旧安排、独立行为证据和必要的成本结果。以源码行数、适配器数量或 processor 接入数量代替收益验收均不成立。

流程收敛围绕可共享的业务事实与准备结果进行。`ProcessCanonical` 当前支持 strict resolver 与 canonical-bytes 键；Block 的 `ResolverBlock` 及其他决策类别不能直接套用。Median、Local、CallRevert、pending-local、Forwarded、写入和订阅保留其执行语义；未来接口调整依据具体设计审定。

## 5. 发布条件与保证范围

稳定发布需要逐方法语义、生成类型、字段交付、错误分类、生命周期及兼容证据共同满足合同。离线回归、本地链和真实 provider 观察分别记账；未覆盖场景保持明确列缺。内部优化完成不自动代表对外兼容或发布通过。

`Corroborated` 表示 provider-backed cross-source evidence（配置来源之间的佐证），不是 Ethereum consensus、canonical chain 或 cryptographic finality 的证明。Selected、Forwarded、pending 本地观察、写入和订阅各自保留其声明的保证范围。
