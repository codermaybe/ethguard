# Adaptive Congestion Control（T11 设计与不变量）

状态：**设计草案（2026-10-31；2026-11-01 补代码基线），新控制器尚未收敛**。决策 0031 只接受方向；本文件把
方向收敛成可实现的不变量、信号、状态和验收矩阵，不选择最终算法参数，也不
改变任何现有行为。

前置边界：

- 决策 0031（自适应拥塞控制方向）；
- 决策 0062（成员固定；健康只影响调度）；
- 决策 0025/0028/0029（调用内冻结基准、固定多数与门槛）；
- [method-contracts.md](method-contracts.md) 0.14 节。

## 1. 目标

在单个 source 的可持续容量以下运行，减少重复限流；通过有界等待、受控恢复
和每源预算，把拥塞反馈限制在**调度层**。目标不是提高吞吐上限，也不是对
provider 容量作出保证。

## 2. 不变量（实现前冻结）

1. **成员不变**：拥塞反馈永不添加、删除、替换或重排投票成员；成员只在
   Client 构造期确定（0062）。
2. **分母不变**：一次调用的投票分母在调用开始时冻结；被调度门暂停的成员
   仍占分母，失败只减少支持，不降低门槛。
3. **权重不变**：每个成员一票；拥塞状态不产生权重、信誉或准确率乘数。
4. **模式/门槛不变**：mode、floor、acceptance threshold 不因拥塞反馈改变。
5. **参考语义不变**：reference tag、freshness 判定和 reference 算法不在
   T11 内改写。
6. **预算共享**：reference 建立、confirm、业务读取、tip probe 和写路径
   预检（若使用同一 source）共享该 source 的调度预算。
7. **等待有界**：等待发送必须受调用 deadline 约束；未获得 slot 的成员记录
   为 unattempted，不产生 source-health 惩罚，也不缩小分母。
8. **不重试**：一次业务调用不因拥塞在 invocation 内重复发送；失败按现有
   fault 分类返回，重试属于上层调用方。
9. **反馈来源**：显式限流（如 HTTP 429）、超时、传输/可用性失败可以影响
   调度；合法 null、admission 合法的 revert、有效 dissent 和 malformed
   content 不 punishing 调度容量。
10. **可观测**：每次调度决策必须能在 observe/诊断中解释（当前速率、等待
    原因、是否获得 slot），但观测不进入 Decision 比较键或 Value。

## 3. 信号与状态

### 3.1 输入信号

| 信号 | 语义 | 对调度的影响 |
| --- | --- | --- |
| `RateLimitError` / HTTP 429 | 显式节流 | 立即降低预算，进入冷却 |
| 调用超时 / deadline | 未知容量或阻塞 | 降低并发/速率，短冷却 |
| 连接失败 / 断连 | 可用性故障 | 暂停新请求，进入 probe 恢复 |
| 成功交换 | 容量证据 | 缓慢增加预算（受上限约束） |
| 合法业务失败（revert/null/dissent） | 非容量信号 | 不改变预算 |

### 3.2 每源状态（概念）

```text
Running(rate, concurrency)
  ├─ Throttled(cooldown, reducedRate)
  ├─ Probing(trialRate)          # 恢复试验流量
  └─ Paused(reason, until)       # 连接/生命周期故障
```

状态转换必须满足：降低立即生效；恢复从降低后的速率开始，不瞬间回到历史
峰值；探测失败重新降低，探测成功才缓慢增加。

## 4. 建议算法族（待比较，不预设参数）

候选实现应在同一状态机下比较：

1. 比例 headroom：目标速率 = 估计容量 × (1 − margin)；
2. AIMD / 慢增快减：成功时小步增加，限流时乘性降低；
3. 并发上限 + 队列：限制同时在途请求数，队列长度有界；
4. 混合：限流时先降并发，再降速率；恢复时先升并发，再升速率。

比较维度：

- 稳定性和振荡（容量变化、突发流量、长时间低负载）；
- 参考建立与业务读取的交互（同一 source 的预算竞争）；
- 共享账号/跨 endpoint 的配额（当前不建模，作为外部约束）；
- 可解释性和参数数量；
- 失败时的保守程度（宁可暂停，不猜测容量）。

具体 margin、增加/降低因子、冷却时长、队列长度、探测定时器均为待定参数，
不得在本文件中写成默认值。

### 4.1 离线定性比较（不选择算法）

| 候选 | 稳定性/振荡 | 恢复行为 | 内存/排队 | 与 reference/业务轮次交互 | 可解释性 | 失败保守性 |
| --- | --- | --- | --- | --- | --- | --- |
| AIMD | 慢增快减，限流后不易立即回到峰值 | 需要 probe/冷却设计 | 无额外队列 | 共享每源预算时，reference 轮次可能被降低后的速率影响 | 参数少，状态可解释 | 限流立即降速，较保守 |
| 并发上限 | 限流下降低在途数，可能仍有突发 | 需要逐步提高并发 | 需要等待/拒绝策略 | 高成本方法会占用并发 slot，可能延长 reference | 中等，需要解释 slot 归属 | 上限可硬保证在途数 |
| 有界队列 | 吸收短突发，长突发会排队 | 队列清空后恢复 | 有明确内存上限 | 队列可能让 reference 与业务互相等待 | 需要解释队列长度/超时 | 队列满时必须拒绝，不能无限等待 |
| 混合（先并发后速率） | 可同时控制突发和在途数 | 先升并发再升速率，状态最多 | 可能同时有队列和并发状态 | 需要明确预算分层，否则 reference 饥饿 | 参数和状态最多 | 失败时较保守，但实现复杂 |

比较结论（仍非算法决策）：

- 当前证据没有持续限流、容量变化、并发上限或队列增长样本，不能据此选择
  任何一个候选或参数；
- AIMD 和并发上限的状态最少，适合作为未来受控实验的候选；有界队列和混合
  控制需要额外回答排队语义和 reference 饥饿问题；
- 任何候选都必须满足 §2 的成员、分母、权重、模式/门槛、reference 和
  不重试不变量。

## 5. 与现有代码的关系

- 现有 `pool` 已有 cooldown、rate 统计、tip sampling 和每源调用预算；
  T11 只在这些调度设施上增加控制器，不改 `Decision`、resolver 或方法计划；
- 现有 `CollectVoting` 的 gated 成员语义保持：未发送请求仍占分母；
- 参考建立（`StrictHeadEstablishment`/`reference.Finalized`）与业务轮次
  共享 source，必须纳入同一预算；
- 实现前先补 inventory 与调度不变量测试，再替换现有静态 cooldown 参数。

### 5.1 2026-10-31 观测

一次只读方法 probe 中，一个公开 endpoint 对 `eth_getBlockByNumber` 的
hash-position 请求返回 `-32029 Too Many Requests`；另一个 endpoint 对
`eth_blobBaseFee` 返回 free-plan 错误，另一个返回非 EVM 策略拒绝。WSS
capture 中一个 endpoint 在协议错误后直接断连，但没有观察到限流。

这些是 provider 的配额/策略信号，不是容量曲线：它们可能来自方法权限、
免费计划或单次配额，而不是持续负载。本轮没有持续压测、超时、队列增长或
并发上限样本，因此：

- 不选择 AIMD、并发上限、有界队列或混合控制的参数；
- 不新增默认 rate/margin/cooldown/queue 常数；
- 不把“一次 429/限流错误”写成 provider 容量结论。

这些观测只确认限流信号真实存在，以及 T11 的输入需要区分“显式配额拒绝”
和“容量反馈”。真实容量样本仍需在受控、低影响的条件下单独采集。

## 6. 验收矩阵（实现阶段）

| 场景 | 期望 |
| --- | --- |
| 稳定容量、低负载 | 不产生虚假惩罚；速率不因无流量自动升高 |
| 持续突发 | 有界等待；超时按 deadline 失败；分母不变 |
| 显式 429 | 立即降低/冷却；冷却后小流量探测 |
| 连续成功 | 缓慢恢复；不越过历史峰值立即恢复 |
| 容量突降 | 快速降低；不出现持续重试风暴 |
| 参考轮 + 业务轮并发 | 同一 source 共享预算；无优先级饥饿 |
| 成员故障/恢复 | 成员集合不变；失败不缩小分母；恢复不改变门槛 |
| 调用取消 | 释放 slot；不惩罚 source |
| 观测 | 每次状态转换和等待原因可解释 |

## 7. 停止条件与未决问题

停止条件：如果实现要求动态成员、权重、模式/门槛变化，或必须把拥塞状态
写入 Decision/Value/比较键，立即停止并回到决策层，不得在 T11 内实现。

未决问题：

- 跨 endpoint/共享账号的配额是否属于同一预算（当前判断：不在本阶段建模）；
- 写路径是否共享读预算（决策 0049 的写路径语义不得被 T11 改写）；
- 队列是否按方法成本分层（feeHistory/block 对象成本高于标量）；
- 观测面的具体指标与采样频率；
- 真实 provider 限流形态与容量估计的证据来源。

## 8. 已有控制器与离线接续入口（2026-11-01）

“T11 未完成”不表示现有 pool 没有自适应调度。`pool/monitor.go` 已有每源
20ms 初始 pace、2ms/2s 下上界、固定两槽并发、每四次成功缓慢减小 pace、
限流加倍/其他 failure 乘 1.5，以及三次连续失败后的 30s cooldown。这些数值
是实现现状，不是本设计新选择的参数，也不代表 provider 的真实容量。

成功业务 rejection（包括合法 revert、method not found）会走健康 success，
因此也参与 pace 恢复。健康可用性证据是否足以触发容量增长，须在 T1 明确；
不能一边保留现状、一边声称只有业务成功提供容量证据。

`pool/scheduling_budget_test.go` 的 `TestSourceBudgetSharedByReadWriteAndAdmission`
以受控 transport 同时占满读/写槽位，再分别驱动 voting read、selected read、
forward、write 和 same-source admission：等待 deadline 不额外发送、不扣 health，
已有调用释放后预算恢复，已取消的等待不会重放。它验证共享预算机制，不是容量曲线、
网络 adapter 证据或完整 T11 验收。tip probe 的具体入口沿用现有 tip 测试，后续
容量阶跃/恢复实验仍须把 probe 与 reference 确认轮纳入同一竞争场景。

基线实验发现并修复：Forward 在最后一个成员尚未获得 source slot 时遭遇调用方
deadline，会落成 `ErrAllSourcesDown`。现在保留调用方 context 错误与 unattempted
emission；不新增发送、重试、failover 或 health 惩罚。该修正不改变真正 fleet
silence 和内部 fan-out timeout 的既有分类。

下一步在同一离线环境补稳定容量、容量突降、恢复、空闲与持续限流的受控实验，
再比较已有算法与候选。没有真实容量曲线时，不宣称找到了通用最优参数；也不必
等待公开 provider 压测才验证算法机制。
